# ВВЕДЕНИЕ

Sangel - это прототип системы для агрегирования групп быстрого реагирования охранных предприятий (ЧОП). Система позволяет клиентам создавать заявки на вызов охраны, группам принимать эти заявки и менять их статус, а операторам контролировать весь процесс.

---

# 1 АРХИТЕКТУРНОЕ ВИДЕНИЕ И КОНТЕКСТ

## 1.1 Описание целей системы

**Бизнес-цели:**
- Создать заявку и найти свободную группу ЧОП в течение нескольких минут
- Позволить клиентам отслеживать статус заявки в реальном времени
- Дать операторам контроль над всеми заявками и группами

**Метрики:**
- Время ответа при создании заявки: менее 1 секунды
- Доступность: не менее 99% времени
- Поддержка 100-200 одновременных пользователей

**Нефункциональные требования:**
- Надёжность: система должна работать даже при сбое одного компонента
- Масштабируемость: возможность добавить новые ЧОП без переделки ядра
- Безопасность: разные права доступа для разных ролей

## 1.2 Контекстная диаграмма

![[imgs_1] Контекстная диаграмма](images/1.png)

**Описание:** Система связывает трёх типов пользователей: клиента, группу быстрого реагирования и оператора. Главное ограничение: одна группа может работать максимум с одной заявкой одновременно. Система отправляет уведомления через SMS и использует карты для определения расстояния.

**Вывод:** Контекстная диаграмма показала, что система - это по сути система распределения задач между исполнителями. Главная сложность не в технологиях, а в синхронизации состояния между заявками и доступностью групп. Я понял, что нужно чётко разделить логику: управление заявками отдельно от управления группами.

# 2 ЛОГИЧЕСКАЯ АРХИТЕКТУРА И ДОМЕННОЕ МОДЕЛИРОВАНИЕ

## 2.1 Выделение доменных областей

Система состоит из трёх независимых доменов:

**1. Order Domain (домен заявок)**
- Отвечает за: создание заявок, смену статусов, историю
- Основные сущности: Ticket (заявка)
- Статусы: NEW → ASSIGNED → IN_PROGRESS → COMPLETED/CANCELLED

**2. Dispatch Domain (домен диспетчеризации)**
- Отвечает за: распределение заявок между группами, управление статусом групп
- Основные сущности: RapidTeam (группа), Assignment (назначение)
- Главное правило: одна активная заявка на группу

**3. Auth Domain (домен аутентификации)**
- Отвечает за: управление пользователями, проверка прав, выдачу токенов
- Основные сущности: User, Role (CLIENT, RAPID_TEAM, OPERATOR)

## 2.2 Главные сущности

**Ticket (заявка):**
- ID заявки
- Описание проблемы
- Местоположение (координаты)
- Приоритет (LOW, MEDIUM, HIGH)
- Статус (NEW, ASSIGNED, IN_PROGRESS, COMPLETED, CANCELLED)
- ID назначенной группы
- Время создания

**RapidTeam (группа быстрого реагирования):**
- ID группы
- Название и контакты
- Текущий статус (IDLE, BUSY)
- Местоположение
- Активная заявка (если есть)

## 2.3 Главные бизнес-процессы

**Процесс 1: Создание и назначение заявки**

1. Клиент создаёт заявку через форму
2. Система ищет свободную группу рядом с местом заявки
3. Если группа найдена - система назначает заявку, группа видит уведомление
4. Если групп нет - заявка остаётся в очереди, система пересчитывает каждые 30 секунд

**Процесс 2: Завершение заявки**

1. Группа завершает работу и отмечает заявку как COMPLETED
2. Группа становится свободной (статус IDLE)
3. Система ищет следующую заявку в очереди

**Вывод:** Выделение доменов помогло понять, что заявки и группы - это две разные истории. Без явного разделения система быстро превратилась бы в запутанный код. DDD показал, что правильная архитектура - это не только про технологии, но про понимание бизнеса.

# 3 АРХИТЕКТУРА МИКРОСЕРВИСОВ

## 3.1 Состав микросервисов

| Сервис | Отвечает за | Основные операции | Данные |
|--------|------------|-------------------|--------|
| **OrderService** | Управление заявками | Создать, обновить статус, отменить, получить | Tickets, History |
| **DispatchService** | Распределение заявок | Найти свободную группу, назначить заявку, освободить группу | Teams, Assignments |
| **AuthService** | Аутентификация | Логин, проверка токена, получить пользователя | Users, Roles |
| **APIGateway** | Маршрутизация | Маршрутизировать запросы, проверить права | - |

## 3.2 Диаграмма взаимодействия
![[imgs_1] Диаграмма взаимодействия](images/2.png)

**Связи:**
- Синхронные (REST): APIGateway → сервисы, быстро
- Асинхронные (события): через Message Broker (RabbitMQ), для слабой связанности

## 3.3 Почему такое разделение?

**OrderService и DispatchService отдельно, потому что:**
- Разные операции имеют разную нагрузку (создание заявки vs поиск свободной группы)
- Разные причины для изменения (бизнес-логика заявок vs алгоритм распределения)
- Возможность масштабировать независимо

**AuthService отдельно:**
- Может переиспользоваться в других системах ЧОП
- Проще добавить интеграцию с LDAP или OAuth

**Альтернатива - один микросервис на всё:** проще разворачивать, но сложнее развивать и масштабировать.

**Вывод:** Правильная граница микросервиса - это не размер кода, а наличие отдельной причины для изменения. Я осознал, что разбиение на микросервисы ради микросервисов - это ошибка. Каждый сервис должен иметь чёткую ответственность.

# 4 АРХИТЕКТУРА ДАННЫХ

## 4.1 Выбор хранилищ

| Сервис | СУБД | Почему |
|--------|------|--------|
| **OrderService** | PostgreSQL | Нужна консистентность и сложные запросы JOIN |
| **DispatchService** | PostgreSQL + Redis | PostgreSQL для истории, Redis для быстрого кэша активных групп |
| **AuthService** | PostgreSQL | Стандартная БД для пользователей |

**Почему не SQLite как в прототипе?**
- SQLite работает до 50-100 одновременных соединений
- PostgreSQL масштабируется до тысяч
- PostgreSQL поддерживает репликацию для надёжности

**Почему Redis?**
- Быстрый поиск доступной группы по геолокации
- Данные горячие (часто читаются, редко пишутся)
- Можно пересоздать из PostgreSQL если сбой

## 4.2 Согласованность между сервисами

**Проблема:** OrderService создал заявку, DispatchService должен её назначить. Как гарантировать, что оба знают о назначении?

**Решение - Saga паттерн:**

1. OrderService создаёт заявку в статусе NEW, публикует событие "TicketCreated"
2. DispatchService слушает это событие, ищет свободную группу
3. DispatchService резервирует группу в своей БД (статус BUSY)
4. DispatchService отправляет запрос OrderService: "Назначь эту заявку группе X"
5. OrderService обновляет статус заявки на ASSIGNED
6. Если что-то сломалось - оба отказываются, система остаётся консистентной

**Результат:** система достигает консистентности через последовательность событий, а не через одну большую транзакцию.

**Вывод:** Распределённые транзакции в микросервисной архитектуре - это сложнее, чем в монолите. Но Saga паттерн показывает, что это возможно. Я понял, что нельзя просто перенести логику монолита в микросервисы - нужно думать по-другому.

# 5 АРХИТЕКТУРА API И ИНТЕГРАЦИЙ

## 5.1 Внешний API для клиентов

**POST /api/tickets** - создать заявку
```
Параметры: описание, местоположение, приоритет
Ответ: ID заявки, статус
```

**GET /api/tickets/{id}** - получить статус заявки
```
Ответ: заявка с текущим статусом, информация о группе
```

**PUT /api/tickets/{id}/status** - обновить статус (для группы)
```
Параметры: новый статус (COMPLETED, CANCELLED)
```

**GET /api/teams** - список доступных групп (для оператора)
```
Ответ: группы с их текущим статусом и местоположением
```

## 5.2 REST API для внешних клиентов

Полное описание всех эндпоинтов находится в `openapi.yml`.

**Основные группы эндпоинтов:**

**Authentication (вход и профиль):**
- `POST /auth/register` - регистрация
- `POST /auth/login` - вход в систему
- `GET /auth/profile` - профиль пользователя

**Tickets (управление заявками):**
- `POST /tickets` - создать заявку
- `GET /tickets` - получить список (фильтруется по ролям)
- `GET /tickets/{id}` - получить заявку
- `PUT /tickets/{id}/status` - обновить статус
- `POST /tickets/{id}/cancel` - отменить
- `GET /tickets/{id}/history` - история изменений

**Teams (управление группами ЧОП):**
- `GET /teams` - список групп
- `GET /teams/{id}` - информация о группе
- `PUT /teams/{id}/status` - обновить статус группы
- `PUT /teams/{id}/location` - обновить местоположение
- `GET /teams/{id}/active-ticket` - активная заявка группы

**ChOP Management (администрирование):**
- `GET /chops` - список ЧОП (только OPERATOR)
- `POST /chops` - добавить новое ЧОП (только OPERATOR)

**Statistics (аналитика):**
- `GET /statistics/tickets` - статистика по заявкам
- `GET /statistics/teams` - статистика по группам

**Контроль доступа на уровне API:**
- Каждый эндпоинт проверяет роль пользователя (CLIENT, RAPID_TEAM, OPERATOR)
- CLIENT видит только свои заявки
- OPERATOR видит всё
- Все запросы требуют JWT токена (кроме регистрации и логина)

## 5.3 Взаимодействие между микросервисами

**OrderService → DispatchService (REST):**
- Запрос: "Найди и назначь свободную группу для заявки X"
- Ответ: ID назначенной группы или ошибка "нет свободных групп"
- Таймаут: 5 секунд (если DispatchService не ответил - заявка остаётся в очереди)

**Через Message Broker (события):**
- OrderService публикует: "TicketCreated"
- DispatchService публикует: "TeamAssigned"
- OrderService слушает: "TeamAssigned" для обновления истории

## 5.4 Интеграция с внешними системами

**SMS уведомления:** система отправляет SMS группе через внешний API

**Карты (Яндекс):** система запрашивает расстояние от группы до места заявки

**Anti-Corruption Layer:** если интегрируемся с legacy системой ЧОП, оборачиваем её API в адаптер, чтобы не засорять наш код

**Вывод:** API должен быть гибким, но строгим - должны быть понятные правила что может делать каждая роль. При проектировании API я осознал, что разделение прав на уровне эндпоинтов важнее чем на уровне БД, потому что клиент часто не предполагает, что у него нет доступа. Anti-Corruption Layer помогает избежать того, чтобы система засорялась code'ом для интеграции с legacy системами.

# 6 КАЧЕСТВЕННЫЕ АТРИБУТЫ

## 6.1 Масштабируемость

**Где узкие места?**
- **OrderService:** если приходит 1000 заявок в секунду, БД может не справиться
  - Решение: несколько реплик сервиса, их нагрузка балансируется

- **DispatchService:** поиск свободной группы может быть медленным (нужно проверить 100+ групп)
  - Решение: кэш в Redis с индексом по геолокации

- **Уведомления:** отправка SMS может быть медленной
  - Решение: асинхронно, очередь в RabbitMQ

## 6.2 Надёжность

**Паттерны для устойчивости к сбоям:**

- **Timeouts:** если сервис не ответил за 5 секунд, считаем это ошибкой, не ждём дальше
- **Retry:** при ошибке повторяем запрос несколько раз
- **Circuit Breaker:** если сервис часто падает, останавливаем попытки к нему на время
- **Fallback:** если главный путь не работает, используем запасной (например, отправляем заявку в очередь вместо прямого вызова)

## 6.3 Безопасность

**Аутентификация:** пользователь логинится, получает токен, отправляет его в каждом запросе

**Авторизация (разные права для разных ролей):**
- CLIENT: может создавать заявки только себе, видит только свои заявки
- RAPID_TEAM: видит назначенные ей заявки, может обновлять их статус
- OPERATOR: видит всё, может управлять чем угодно

**Защита:** все запросы только через HTTPS, API ключи хранятся на сервере

## 6.4 Наблюдаемость

**Логи:** структурированные логи со временем, названием сервиса, типом события (для анализа)

**Метрики:** сколько заявок создано, среднее время обработки, количество ошибок

**Трассировка:** когда запрос идёт через несколько сервисов, можем увидеть, где он залипал

**Алерты:** если что-то ломается (много ошибок, медленный ответ), система уведомляет администратора

**Вывод:** Наблюдаемость в микросервисной архитектуре критична. Когда система состоит из 10 сервисов, логи в одном файле уже не помогают. Правильные метрики - это глаза администратора.

# 7 ИНФРАСТРУКТУРА И РАЗВЁРТЫВАНИЕ

## 7.1 Выбор платформы

**Облако (AWS, Yandex Cloud) + Docker контейнеры + Kubernetes**

**Почему не на своих серверах?**
- Нужно администрировать железо (дорого, требует специалистов)
- Сложно масштабировать (нужно покупать новый сервер)

**Почему Kubernetes?**
- Автоматически запускает несколько копий каждого микросервиса
- Автоматически перезапускает упавший сервис
- Распределяет нагрузку между копиями

**Альтернатива:** просто виртуальные машины (проще начать, но сложнее масштабировать)

## 7.2 Окружения

**Dev (локальное):** всё на компьютере разработчика через Docker Compose

**Test:** автоматические тесты на каждый PR

**Stage (промежуточное):** копия продакшена, здесь тестируем перед выпуском

**Prod (боевое):** реальная система для пользователей, высокая доступность (несколько копий каждого сервиса)

## 7.3 Выпуск новых версий

**Стратегия: Canary deployment**

1. Новая версия запускается для 5% пользователей
2. Мониторим ошибки: если нормально → для 25% → 50% → 100%
3. Если ошибок много → откатываемся на старую версию

**Преимущество:** новая версия сломалась? Затронула только 5% пользователей, остальные не заметили.

## 7.4 Непрерывная интеграция (CI/CD)

Процесс автоматический:
1. Разработчик пушит код в GitHub
2. Автоматически запускаются тесты
3. Если тесты прошли → собирается Docker образ
4. Образ отправляется в registry
5. Автоматически развёртывается в stage окружение
6. Если всё хорошо → можно вручную нажать кнопку Deploy to Prod
7. На prod запускается canary deployment

**Вывод:** Инфраструктура и автоматизация - это то, что превращает архитектуру из диаграмм в работающую систему. Правильный выбор платформы позволяет сосредоточиться на разработке, а не на администрировании серверов. CI/CD pipeline гарантирует, что в production попадает только тестированный код.

# ЗАКЛЮЧЕНИЕ

Микросервисная архитектура Sangel решает реальные проблемы растущей системы:

1. **Независимое развёртывание** - команда разработчиков может выпускать изменения в OrderService без влияния на DispatchService

2. **Масштабируемость** - если нагрузка на поиск групп выросла, мы масштабируем только DispatchService, а не всю систему

3. **Надёжность** - если DispatchService упал, новые заявки создаются, они просто останутся в очереди (при восстановлении сервиса будут обработаны)

4. **Гибкость** - можно заменить DispatchService на другую реализацию без изменения OrderService

Но эта архитектура сложнее монолита:
- Нужно тщательнее мониторить систему
- Сложнее отлаживать проблемы (запрос проходит через несколько сервисов)
- Нужно думать о согласованности данных иначе

Главное, что я извлёк: архитектура - это выбор компромиссов. Монолит проще разворачивать, микросервисы проще масштабировать. Для каждого проекта нужно выбрать то, что подходит именно ему.

   └─ OrderService: обновляет ticket.status = "IN_PROGRESS"
